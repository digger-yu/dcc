# Backend Feature Matrix

> **第一性原理**：能力矩阵的唯一 truth 是「`dcc` 产物里到底有什么」，不是本文件，
> 也不是 `src/codegen/features.rs` 里的手工声明。本文件里带
> `BEGIN/END GENERATED BY` 标记的两张表**全部由脚本生成**，手改会被 CI 判红。
>
> 复算入口：`bash scripts/probe_backend_features.sh -o md`
> 门禁入口：`bash scripts/probe_backend_features.sh --check docs/backend_feature_matrix.md`
>
> 生成块里**故意不含时间戳**（历史版本的 `probe @ $(date -Iseconds)` 字面量从未被
> shell 展开过，而且任何时间戳都会让 diff 断言永远不可能成立）。

## 图例（符号与**证据级别**绑定，不是装饰）

| 符号 | 含义 |
|---|---|
| `✅` | artifact 级证据成立：产物里有可指纹化的证据（节名 / UND 符号 / ELF-COFF 头），**可作门禁依据** |
| `❌` | artifact 级证据缺失，且该判据本身足以证否（例如要求 `.tdata` 节但没有） |
| `◐` | 仅 accept 级证据：dcc 接受该构造并发出了非空 `.text`。**抓不到「静默 no-op」**，不得当支持性结论 |
| `✗` | accept 级判据未通过：`dcc` 直接报错（E0xxx）或产物为空 —— 这是**确凿的否定** |
| `?` | 该架构 `-c` 产物**容器不可解析**（宿主 objdump 拒绝），无法判定；**不等于不支持** |
| `—` | 探针弃权：该能力在单个 `-c` 产物里根本没有可观测指纹（例：`ParallelCodegen` 只在多进程链接期可见） |

`声明` = `src/codegen/features.rs` 里该架构所用 `FeatureSet::*()` 构造函数解析出的 token 集。
第二张表同样是机器生成的，**不要手抄**。

## 三方一致是怎么被钉住的

```
dcc 实测产物  ==  本文件生成块  ==  FeatureSet::*() 声明
```

* **边 1（文档 == 实测）**：`--check` 把生成块与文件里的块做 `diff -u`，任何漂移即红。
* **边 2（文档 == 声明）**：声明矩阵本身就来自 `features.rs` 解析，因此同一次 `diff` 顺带覆盖。
* **边 3（实测 == 声明）**：逐格断言，规则按证据强弱分档——
  * `artifact` 级实测 `❌` 而声明了 → **FAIL**（言过其实）；
  * 任意级别但 `dcc` 直接报 `E0xxx` 而声明了 → **FAIL**（编译被拒绝不是弱证据）；
  * `accept` 级 `✗`（非编译错误类）而声明了 → 只告警；
  * `artifact` 级实测 `✅` 而未声明 → 只告警（`tier2_cross()` 是 arm/mips/mips64
    的**交集**，下取整是合法保守，不算错）；
  * `?`（容器不可解析）不参与比对，但**单独构成一条硬失败**——见下节。
* 另外两条结构性防漏断言：`Feature` 枚举里任何被声明的 token 若**没有判据** → 直接
  `exit 2`（新增能力位却忘了写探针 = 自动盖章，禁止）；`cli.rs` 推导的已注册架构数若
  与 `registry.rs::backend_for()` 的 `Some(` 分支数不等 → `exit 2`（历史上 CI 那步写死了
  `expected_backends=22`，本地永远算成 22 vs 6，是**结构性恒红**的假门禁，已删除）。

探针退出码分档（把「已知缺陷」与「矩阵说谎」分开，否则门禁会被已知缺陷磨成噪音）：

| 码 | 含义 |
|---|---|
| 0 | 三方一致，且无容器不可解析的后端 |
| 1 | **矩阵说谎**：文档漂移 / artifact 级实测 `❌` 却仍声明 / 声明的 Feature 无判据 |
| 2 | 用法错误或环境缺失（dcc / fixture / readelf / objdump） |
| 3 | 三方一致，但存在**容器不可解析**的后端产物（现状：无；保留这一档是为了以后有人把某个后端的容器改坏时，仍能与「矩阵说谎」区分开）|

## 曾经的唯一红：mips64 的 ELF 容器（已修，探针现 exit 0）

`dcc --target mips64-linux-gnu -c` 的 `.o` 曾被宿主 `objdump -h` 以
`file format not recognized` 拒绝，因此 mips64 那一列**全部**是 `?`。根因与
`tests/integration.rs::non_x86_c_mode_produces_valid_elf` 的红是同一个事实：
`e_ident[EI_DATA]` 写 `ELFDATA2MSB`，而 ELF 头/节头表/symtab/rela 的数值字段一律按小端落地
（见下节「已知行为分歧」第 5 条）。现在正文与文件自己的声明一致了，实测 `readelf -h` →
`ELF64 / 大端序 / REL (可重定位文件) / MIPS R3000`，`objdump -h` rc=0（文件格式 `elf64-big`），
mips64 那一列 25 格拆成 `✅×4 / ❌×7 / ◐×10 / ✗×2 / —×1`，全局 `?` 归零。
两条边界必须说清楚：
① **指令流一个字节都没动**：mips64 的 `-S` 输出在修复前后 0 漂移，坏的只是容器；
② 容器可解析 **不等于** 调试信息可解析：mips64 的 `.debug_info` unit length 与
   `.eh_frame` FDE length 仍是小端，那是 `src/debug.rs` 的载荷层，见「已知行为分歧」第 8 条。

## Tier 分类

- **Tier-1 交叉**（aarch64 / riscv64）：核心语言特性 + DWARF + `.eh_frame` 有产物指纹。
- **Tier-2 交叉**（arm / mips / mips64）：只有核心算术、调用约定、DWARF/CFI；
  `Tls`/`Lto`/`Trapv`/`Vector`/`Atomics`/`Int128` 实测无指纹。
- **Disabled**（riscv32）：`Arch::has_backend() == false`，已从 registry 摘除，
  探针因此**不覆盖**它（矩阵里没有列 = 未注册，不是漏测；这一条由 `cli.rs` 推导保证）。

## 探针方法论

* 输入是 `tests/fixtures/probe/*.c` 里的**能力隔离** fixture，不是 `tests/fixtures/c/`
  里同名主题的文件。原因（实测）：`tests/fixtures/c/bitfield.c` 掺了 `sizeof(struct)`，
  在 aarch64/riscv64 上因 `E0312 SizeAlignOffset` 编译失败，用它探 `Bitfield` 会得到
  **假阴性**。同理避免下标（`E0314`）、libc include（交叉目标无 sysroot）。
* 每个 fixture 只暴露一种能力，判据只看产物指纹，不看 stdout。
* 历史版本的 `tests/input/` 目录**根本不存在**，旧探针因此 50/50 全是
  `MISSING_FIXTURE` 却恒返回 0；调的又是 `gcc -cc1`（gcc 没有 `-cc1`），从未碰过 dcc。

### 探针目前**覆盖不到**的能力位（诚实声明）

| Feature | 为什么覆盖不到 | 现在怎么处理 |
|---|---|---|
| `ParallelCodegen` | 只有多进程/链接期行为才可见，单个 `-c` 产物无指纹 | 矩阵里恒 `—`（弃权），不参与门禁 |
| `RiscVBorrowedRegs` | 是寄存器分配策略，产物里无稳定指纹 | 同上 |
| `Atomics` / `Vector` / `Int128` / `Bitfield` / `VaList` / `CoreArith` / `Float` / `LongDouble` / `InlineAsm:*` / `BoundsCheck` | 「接受并生成非空 `.text`」**不能**证明语义正确，只能证明没被拒绝 | 标 `◐`，**不进门禁**；要证否需要链接后跑起来（依赖宿主 QEMU 与 libc，属下一轮）|
| `Sanitizer(*)` / `Trapv` / `StackProtect` | 判据是 UND 引用，能证明「插桩发出了调用」，但不能证明运行期真的 trap | 已算 artifact 级，但注意其含义边界 |
| `Dwarf(4)` | 探针只判 `.debug_*` 节**存在**，不校验 DWARF 版本字节与行表可解析性 | `✅` 表示「发出 DWARF 节」，不表示 `gdb` 能读 |

## 已知行为分歧（本文件**不**粉饰，逐条待独立决策）

1. **extern 声明被物化成本 TU 函数定义**（本条的 `-c` 半句**已被本轮实测推翻**）：
   `int callee(int);` + 调用，在 aarch64/riscv64/mips 上 `-S` 仍会输出 `callee:` 标签与
   空函数体（`-S` 走的是脚手架式打印，与 `-c` 不是同一条发射路径）。
   但「`-c` 产物里没有 UND `callee`」是**假阴性**：那是第 6(A) 条整表错位让
   `readelf -sW` 根本读不出符号名造成的，不是没有。修好第 6 条后实测 aarch64/riscv64 的
   `-c` 产物里有 `FUNC GLOBAL DEFAULT UND callee` ⇒ 矩阵里这两格从 `❌` 变 `✅`。
   仍然为真的是：mips64 与 arm/mips32 的 `-c` 把 `callee` 发成**已定义**符号
   （`Ndx=1`，非 UND），且**不发任何跨 TU 重定位** —— 这是 codegen 层的绑定/重定位
   缺口（arm/mips 的 `ensure_sym` 把 extern 调用目标当本 TU 已定义），不是第 6 条
   那个 ELF32 字段顺序假阴性（该顺序本轮已修，`callee` 不再被读成 `Type=FILE`）。
   → 「`CoreCall` 已从 `tier1_cross()`/`tier2_cross()` 删除」这一声明现在**偏保守**：
   aarch64/riscv64 的 `-c` 侧证据已成立；arm/mips32 的 `CoreCall` 仍应判 ❌，但理由
   已从“读不出符号”的假阴性换成“callee 非 UND 且无重定位”的真实缺口（另立条目）。
2. **交叉后端 symtab/strtab 字符串偏移越界**（ELF64 侧已随第 6 条消解；ELF32 侧仍在）：
   `objdump -t` 曾对 aarch64 报 `invalid string offset 256 >= 15 for section '.strtab'`。
   复核后它**不是独立的 strtab 缺陷**，而是第 6(A) 条「空符号 25 字节 ⇒ 整表错位」把
   `st_name` 读成越界偏移的下游症状；现在 aarch64/riscv64 的 `objdump -t` 正常列出
   `callee`（`*UND*`）与 `caller`（`.text`）。arm 那一半此前**仍在**（`caller` 仍被读成
   `<操作系统专用>：12 <未知>：3`），根因是第 6 条末尾那条 ELF32 字段顺序缺陷 ——
   本轮修后 arm/mips32 的 `objdump -t`/`readelf -sW` 均已干净。
3. **`.debug_info` 重复发射**（本轮已修）：`{aarch64,arm,mips,mips64,riscv64} -g -c`
   的 `.o` 里原有**两个**同名 PROGBITS 节（内容逐字节相同），x86_64 正常。根因是
   `src/debug.rs::dwarf_elf_sections()` 已发过一遍，5 份 `build_aux_sections()`
   又各自手工 push 一遍；现在只留共享生产者（取舍见 `aarch64/backend.rs` 里那一处的
   注释：不给 `push_extra_section` 加同名去重，那会把未来有意的重复一并吞掉）。
   实测（`tests/fixtures/probe/core_call.c`，`-g -c`，格式为 节数/字节）：
   aarch64 `2/11/2472` → `1/10/2304`，arm `2/9/1604` → `1/8/1416`，
   mips `2/9/1668` → `1/8/1480`，riscv64 `2/11/2440` → `1/10/2272`，
   mips64 `2056` → `1848`（**当时**容器仍不可解析，其重复度改按 shstrtab 里 `.debug_info`
   出现次数计：2 → 1），x86_64 `1/15/3064` 不变。全量 drift：7968 组合里 1106 格
   漂移，**全部**是 `-g -c` 且**只**落在这 5 个交叉架构上（x86_64 全模式 0 漂移，
   `-c`/`-S`/`-O2 -c` 共 5976 格 0 漂移）。
4. **host-link 模式不可复现**（本轮已修）：临时 `.o` 原名
   `dcc-hostlink-<pid>-<src>.o`，宿主 ld 按 basename 登记 `STT_FILE` 而把 PID 泄进最终
   产物。现在 PID 只留在**目录**部分（`/tmp/dcc-hostlink-<pid>/dcc-hostlink-<src>.o`），
   basename 只含稳定量。实测：`stmt_expr.c -O0` 连跑 5 次，修复前 5 个不同 sha256 /
   修复后 1 个；8 个进程并发编同一源也只得 1 个哈希。
   **触发条件（实测）**：TU 必须含文件作用域 `static`，否则 ld 根本不为该 `.o`
   登记 `STT_FILE`，这条通道没被走到（回归锁的 fixture 因此专门带了 static）。
4b. **要求 COFF 却静默给 ELF**：`--target {aarch64,riscv64,arm,mips,mips64}-w64-windows-*`
    全部被 `Target::resolve` **接受**（不报 E 级错误），但 `od -An -tx1 -N2` 读出来仍是
    `7f45`（ELF magic）而不是 COFF 的 `6486`。只有 x86_64 真产 COFF。
    → `ObjectFormat:Coff` 那一行用**各自架构的 windows triple** 去问（不是用 Linux
    triple 探“默认容器”），矩阵里的 `❌` 因此是真的。真正该修的是这些
    windows triple 应当被拒绝、而不是静默降级。
5. **mips64 ELF64 容器端序自相矛盾**（已修）：`src/codegen/elf.rs::build_elf_rel_generic()`
   曾收下 `ei_data` 只写进 `e_ident`，其余数值字段一律 `to_le_bytes()`；mips64 是唯一
   以 `ELFDATA2MSB` 调它的人，于是 `readelf -h` 把 `e_type` 读成 `0x100`、
   `e_machine` 读成 `0x800`、`e_shoff` 读成 `576742227280134144`，`objdump -h` 直接拒绝。
   现在 ELF 头 / 节头表 / `Elf64_Sym` / `Elf64_Rela` / `SHT_GROUP` 一律经 `is_be` 感知的
   `ew_u16/ew_u32/ew_u64/ew_i64` 落地，`write_section_header()` 新增 `is_be` 形参（与
   ELF32 侧 `write_section_header32()` 对称）。实测同一份 `int main(void){return 0;}`：
   修复前 712 字节、`objdump -h` rc=1；修复后**仍 712 字节**（只有内容变），
   `readelf -h` → `ELF64 / 大端序 / REL / MIPS R3000 / 7 个节头`，`objdump -h` rc=0。
   注意**指令流本身已经是大端**（`src/codegen/mips.rs` 里 62 处 `to_be_bytes`），
   坏的只是容器 ⇒ 本轮**没动也不应该动**指令编码（mips64 `-S` 模式 0 漂移即证据）。
   护栏实测：x86_64/aarch64/arm/mips/riscv64 逐 arch
   `MODES='-c|-S|-g -c|-O2 -c'` drift 各 1328 组合 = 6640 组合 **0 漂移**；
   mips64 同条件下 661 组合漂移（全在 `-c`/`-g -c`/`-O2 -c` 三类，`-S` 0 漂移）。
   → 注：那条护栏的**本意是防意外改动，不是禁止有意修真实 bug**；下一轮（第 6 条）
   经使用者明确授权改变 aarch64/riscv64 的产物字节，护栏逐 arch 重测见第 6 条末尾。
6. **ELF64 `.symtab` 的四项 gABI 违规**（**本轮已全部修掉，BE/LE 分叉已彻底消除**）：
   缺陷都在 `src/codegen/elf.rs::build_elf_rel_generic()`（aarch64/riscv64/mips64 共用的
   ET_REL 生产者），同时错四处，每一处都独立让 `readelf -sW` / `objdump -t` /
   dcc 自研链接器（`src/link/object.rs` 按 24 字节步进）读错：
   * **(A) 条目尺寸**：首条空符号按 `st_name(4)` + 填充 + `st_value(8)` 拼装，填充量还按
     端序分叉（MSB 给 12、LSB 给 13）。`Elf64_Sym` = 4+1+1+2+8+8 = **24** ⇒ 填充只能是
     12 ⇒ LE 下空符号是 **25** 字节，其后每条符号整体错位一格。全零填充本就与端序
     无关，那个 `if is_be` 分叉从一开始就不该存在 ⇒ 现已删分叉、一律 `&[0u8; 24]`。
   * **(B) 位域**：`st_info` 只写 `sym.ty`（`STB_* << 4` 一个比特都没放进去），`bind` 反而
     被塞进 `st_other`（还多带 `visibility << 4`）⇒ 所有符号被读成 `STB_LOCAL` + 凭空的
     `STV_INTERNAL/HIDDEN`。与端序无关，**三个共用该函数的 arch 全中招**。
   * **(C) `sh_info`**：`.symtab` 节头 `sh_info` 写死 `1`，gABI 要求它 = 首个非局部符号
     下标 = 局部符号数（含下标 0 空符号）。实测含 `static` 的 aarch64/riscv64 TU 真值是
     `3` 而旧代码写 `1`。mips64 **逃过一劫**：`src/codegen/mips.rs` 不产 `STB_LOCAL`，
     n_locals 恒为 0 ⇒ `1` 恰好等于真值（所以它在 core_call 上不报这条警告）。
     x86_64 **本来就对**：走 `build_elf_rel_x86_64()`，该函数已实算 `n_locals`。
   * **(D) 排布**：符号按前端发射顺序原样落地，不做 LOCAL-first 排序，也不重映射
     `.rela.*` 的 `r_info` 符号槽。实测旧序（`static int helper` + `int gsrv` 的 TU，
     从 `.strtab` 字节序直接读出）：`gsrv`(G) → `.rodata`(L) → `helper`(L) → …，
     LOCAL 夹在 GLOBAL 之后 ⇒ 即使 (C) 修对了也违反 gABI，链接器会误把 static 当可导出。
   (B)(C)(D) 互相遮掩：只修 (A) 时 readelf 仍把每个符号读成 LOCAL，
   `local symbol N found at index >= .symtab's sh_info value of 1` 警告原样保留 —— 这正是
   上一轮“只修 MSB”后 mips64 仍半坏的原因。四条一起修才收敛。
   实测判据（`tests/fixtures/probe/core_call.c` `-c`）：

   | arch | 修复前 | 修复后 |
   |---|---|---|
   | aarch64 | `sh_size=0x49`(73，非 24 倍数)、`ES=24`、`Info=1`；两条 `NOTYPE LOCAL HIDDEN` + `BAD[0x101]`、名字乱码、2 行警告；`objdump -t` 报 `invalid string offset` | `sh_size=0x48`(72)、`ES=24`、`Info=1`；`FUNC GLOBAL DEFAULT  UND callee` / `FUNC GLOBAL DEFAULT  1 caller`；**0 警告** |
   | riscv64 | 同 aarch64（`sh_size=0x49`） | 同上，**0 警告** |
   | mips64 | 已对齐（`sh_size=0x48`）但 `FUNC LOCAL INTERNAL`（bind 丢失） | `FUNC GLOBAL DEFAULT`，**0 警告** |
   | x86_64 | 走另一条路径，四项本来都对 | **逐字节不变**（drift 实测 0 组合） |

   含 `static` 的 TU（验证 (C)(D)）：aarch64/riscv64 旧 `sh_size=0xa9`(169)、`Info=1`、
   7 行警告；新 `sh_size=0xa8`(168 = 7×24)、`Info=3`、`.rodata`/`helper` 两个 LOCAL 排在最前、
   无警告。
   影响面逐 arch drift（`MODES='-c|-S|-g -c|-O2 -c'`，各 1328 组合）：x86_64 **0**、
   arm **0**、mips32 **0**（本轮未碰 ELF32，零漂移即证据）；aarch64 687 / riscv64 687 /
   mips64 645 格漂移，且经逐节 `dd`+sha256 归因，**只**落在 `.symtab` / 节头表（仅
   `sh_info`/`sh_size` 字段）/ `.strtab`（仅符号名顺带重排）/ `.rela.text`与`.rela.rodata`
   （仅 `r_info` 高 32 位的符号槽号）/ ELF 头（因对齐变化导致 `e_shoff` 移动），
   `.text` / `.rodata` / `.eh_frame` **逐字节未变**。
   → 回归锁 `tests/integration.rs::elf64_symtab_matches_gabi_layout`（纯字节 gABI 断言 +
   `readelf -sW` stderr 必须空 + `objdump -t` 第二独立读者）。把 (A) 改回 25 字节即可让它
   变红（实测：`sh_size = 73 不是 24 的倍数` + 原样复现两行警告）⇒ 锁是活的。
   **ELF32 侧同族缺陷（本轮已修）**：`build_elf32_rel_generic()`（arm/mips32 共用）
   此前把 `Elf32_Sym` 按 **ELF64 的字段顺序**落地，而两者的排布**不同** ——
   `Elf32_Sym` = `st_name(4)+st_value(4)+st_size(4)+st_info(1)+st_other(1)+st_shndx(2)`。
   下标 0 全零空符号“碰巧”两种排布一样，于是缺陷被隐藏；真符号却被 binutils 读成
   `st_value=0x10002`、`Type=FILE`、`Ndx=BAD[...]`（实测 mips32 `core_call.c -c` 曾报
   `st_value=0x12000001`/`BAD[0x28]`，arm 把 `callee` 读成 `FILE`）—— 探针里 arm/mips 的
   `CoreCall`、`Sanitizer:*` 等 `und_sym` 格子长期**假阴性**的真因就是这一条字段顺序，
   不是排序。本轮与 (C) 一并按 ELF32 正确排布重写，并补上 local-first 稳定排序 +
   `.rel.*` 符号槽重映射 + `sh_info` 实算（此前写死 1）。同轮把 arm/mips32 的
   **static 函数**从无条件 `STB_GLOBAL` 改为按 AST `is_static`/`is_weak` 定 `STB_LOCAL`/
   `STB_WEAK`（判据抄 aarch64/riscv64/mips64，它们本就正确），使 arm/mips32 `.o` 里
   `static int priv(void)` 终以 `FUNC LOCAL` 出现。实测（`tests/fixtures/probe/core_call.c`
   等价样例 `-c`）：arm `priv`→`FUNC LOCAL 1`、`pub`→`FUNC GLOBAL 1`；mips32 同；
   `readelf -sW`/`objdump -t` 均干净读出符号名、0 警告、无 `BAD[`。drift 严格落在
   arm/mips32 的 `.symtab`/`.strtab`/节头表，`.text`/`.eh_frame` 不变；x86_64/aarch64/
   riscv64/mips64 逐字节不变（未走这条 ELF32 写者）。回归锁
   `tests/integration.rs::elf32_symtab_matches_gabi_layout`（纯字节 Elf32 排布断言 +
   `readelf -sW` stderr 空 + `objdump -t` 第二读者）。
   **本轮又推进一步（item 4 变量侧）**：aarch64/riscv64 的 `emit_global` 此前
   无条件把文件作用域变量发成 `STB_GLOBAL`，现改为按 AST 判定：`static int gs;`
   （顶层 `Decl::Var.is_static`）与函数内 static local（`Global::is_static_local`）
   都发 `STB_LOCAL`，其余仍 `STB_GLOBAL`。未改 IR，只在后端查 `prog`（与
   `find_func` 对函数同一手法）。实测 `static int gs`/`int pub`/`int get()`：
   aarch64/riscv64 均 `gs → OBJECT LOCAL`、`pub → OBJECT GLOBAL`，x86_64（自有写者）
   本来就对 ⇒ 作为语义参照。回归锁：`elf64_symtab_matches_gabi_layout` 新增
   “mixed 用例的 `gsrv` 必须以 LOCAL OBJECT 出现”断言（仅对会发全局变量符号的
   x86_64/aarch64/riscv64 断言）。
   **交叉链接+运行期验证已落地（本会话新增）**：装 `binutils-aarch64-linux-gnu` +
   `qemu-user-static` 后，可用交叉 `as`/`ld` 链接 dcc 产物并在 qemu 下真跑。
   由此发现并修复了 aarch64 函数调用的四个叠加 codegen bug（非叶子不存 lr /
   `mov_w_reg_w0` 目标源颠倒 / `patch_bl` PC 基准多 4 / 多实参互覆 x0），现单 TU
   多参、嵌套、跨 TU 调用均正确退出（回归锁 `aarch64_cross_call_runs_under_qemu`）。
   这与重定位无关 —— aarch64 的 `R_AARCH64_CALL26` 本就对。
   **仍待决策**：(a) arm/mips32/mips64 后端**根本不发文件作用域变量符号**
   （`emit_global_init` 只写 rodata 字节、不 push ElfSym）；(b) arm/mips32/mips64
   后端对跨 TU 引用**完全不发重定位**（`extern` 调用被当已定义符号、`.rel.text`
   恒空；arm 的 `pending_bl_calls` 推入后从未排空），且尚未做与 aarch64 同类的
   ABI/实参修正；(c) 二元表达式内同时含两个调用（如 `fib(n-1)+fib(n-2)`）的
   中间值跨调用溢出尚未实现，aarch64 递归仍会错/崩——这些都是比容器更深的
   codegen 缺口，需逐后端移植上面的修正 + 补溢出（见第 7/8 条）。
7. **交叉后端的 `-g` 产物没有 `.rela.debug_*`**：实测 `tests/fixtures/probe/core_call.c`
   `-g -c` 的重定位节集合，x86_64 = `[.rela.debug_aranges .rela.debug_info .rela.debug_line
   .rela.text]`，aarch64/riscv64/mips64 = `[.rela.text]`，arm/mips32 = `[.rel.text]`
   ⇒ 5 个交叉后端一个都没有。后果：DWARF 里的地址字段（`DW_AT_low_pc`、行表地址、
   `debug_aranges` 块）是**裸写常量**，链接期无处回填（x86_64 的 `DW_AT_low_pc: 0` 是
   带着重定位的 0，交叉后端的 0 是焊死的）。本机无交叉 gdb / pahole / qemu-user，
   **无法本机确证真实调试器行为**；`readelf -u` 对交叉产物只能给出“不支持该架构的
   unwind 解码”。→ 待独立决策（修法方向：给 `src/debug.rs` 的每个地址字段发一条指向
   所在函数的重定位，并让 `push_extra_section` 按节名产出 `.rela.debug_*`）。
8. **mips64/mips32 的 DWARF/CFI 载荷仍是小端**（本轮未动）：容器修好后暴露出下一层——
   `readelf --debug-dump=info` 对 mips64 报 `Corrupt unit length (got 0x82000000,
   expected at most 0x82)`，`--debug-dump=frames` 报 `Invalid length 0x10000000 in FDE`。
   根因在 `src/debug.rs`（DWARF unit length、`build_eh_frame_with_arch` 的 CIE/FDE 长度与
   偏移）一律 `to_le_bytes()`，没有像 elf.rs 那样按目标端序分叉。修法与第 5 条同范式
   （`is_be` 分叉），代价按护栏只落在 mips32/mips64 的 `-g` 产物上；本轮不扩大范围。
