# DCC 解析器性能优化全局方案

## 当前架构概述

DCC 解析流程：`source bytes → preprocessor → lexer/tokenizer → recursive descent parser → AST`

主要热点方向：
1. 大量小对象分配 → 内存分配/释放 overhead 高。
2. 词法分析逐字节处理，字符分类分支多 → 分支预测差。
3. 预处理器字符串拼接和宏展开 → 频繁分配拷贝。
4. 递归下降解析中表达式递归太深 → 栈 overhead。
5. 字符串比较 hash 未优化 → 符号表查找慢。

---

## 分层优化方案

### 第一层：内存分配优化（见效快，改动小）

#### 1. Arena 分配器替换 `Box`/`Vec` 用于 AST 节点

**问题**：当前 AST 每个节点 `Box::new`，大量小分配 overhead 大。

**方案**：
- 在 parser 中分配一个或多个 `Arena` (线性分配器)。
- 所有 AST 节点、字符串 slice 都从 arena 分配。
- 解析完成后，整个 AST 用一个 `drop_arena` 一次性释放。
- 不需要每个节点单独 drop，节省 drop 时间。

**改动范围**：
- AST 定义修改：将 `Box<T>` 改为 `&'ast T`，生命周期绑定到 arena。
- Parser 持有 arena，所有 `Box::new` 改为 `arena.alloc`。

**收益**：减少 ~30%-50% 分配调用，降低碎片化，分配速度提升数倍。

---

#### 2. Token 预分配缓冲区

**问题**：当前 token 每次分配，可能很多小分配。

**方案**：
- 预分配 `Vec<Token>`，保留容量，解析时直接 push，避免频繁 realloc。
- 对于大文件，预估行数，初始容量设置为行数 × 系数。

---

### 第二层：词法分析优化

#### 1. 查表法替换字符分类分支

**问题**：当前对每个字符做一系列 `if is_alpha(c) ... else if is_digit(c) ...` 分支，分支预测差，指令多。

**方案**：
- 启动时预先生成一个 256 项的查找表 `u8 char_class[256]`。
- 每个字节查表直接得到分类：identifier/digit/space/operator/punctuation。
- 无分支，一次内存命中得到分类，分支预测 miss 减少 90%+。

**实现**：
```rust
enum CharClass {
    Invalid,
    IdentStart,  // a-z, A-Z, _, $
    IdentCont,   // 上面加 0-9
    Digit,       // 0-9
    Dot,         // .
    Punct,       // ()[]{};, etc.
    Op,          // +-*/=<>!&|^%
    Space,       // whitespace
    Eof,
};
CharClass CHAR_CLASS[256];
```

**收益**：词法分析速度提升 ~20%-30%。

---

#### 2. 块读取预读，减少单字节处理

**问题**：当前代码逐字节 peek/consume，每次都做边界检查。

**方案**：
- 维护一个 64B 或 128B 的预读缓冲区，每次从 source 批量读入。
- 只有缓冲区空了才去 source 拿新块，减少边界检查次数。
- 使用 unsafe 直接索引缓冲区（保证不越界）。

---

#### 3. 标识符快速比较+小型哈希

**问题**：当前符号表查找每次全字符串比较，hash 计算慢。

**方案**：
- 对短标识符 (<= 16 字节) 使用 64 位/128 位指纹直接比较，避免访问字符串内存。
- 预计算标识符哈希在 lexer 阶段，parser 直接使用。
- 使用快速多项式哈希，或 siphash，避免编译器 strlen 调用。

---

### 第三层：预处理器优化

#### 1. 宏展开缓冲区复用

**问题**：每次宏展开分配新字符串，展开后又丢弃，分配 overhead 大。

**方案**：
- 预处理器持有一个 `Vec<u8>` 工作缓冲区，宏展开写入后复制出去，再 clear 复用。
- 对于嵌套展开，递归复用缓冲区，减少分配次数。

---

#### 2. 字符流惰性读取

**问题**：预处理器一开始就把整个源文件读到内存，然后展开所有宏，生成一个巨大的token流。大文件内存占用高。

**方案**：
- 保持当前一次读取整个文件（简单），但 token 生成惰性，parser 请求一个 token 再生成一个。
- 不提前生成整个 Vec<Token>，减少峰值内存。

---

### 第四层：递归下降解析优化

#### 1. 表达式优先级转换为 Pratt 解析器

**问题**：当前递归下降处理表达式，优先级用递归实现，每层递归都分配栈帧，深度表达式会爆栈且慢。

**方案**：
- 将表达式解析改为 Pratt 解析器，基于 token 优先级表循环处理，不需要多层递归。
- 减少栈溢出风险，分配栈帧次数减少，速度提升。

**适用范围**：
- 所有二元表达式：加减乘除比较逻辑移位位运算。
- 三元表达式 `a ? b : c` 也适用。

**改动范围**：
- 只改 `parse_expr` 相关函数，不碰其他解析逻辑。
- 保留递归下降处理语句和声明，只改表达式解析路径。

---

#### 2. 公共前缀剪枝+错误恢复缓存

**问题**：错误恢复每次都从头扫描，重复工作多。

**方案**：
- 记录同步点，错误恢复跳到最近同步点，减少重复扫描。
- 对常见语法错误提前预判，减少回溯。

---

### 第五层：数据结构重构

#### 1. Token 打包紧凑化

**问题**：当前 Token 可能有大的 alignment gap，内存浪费，缓存命中率低。

**方案**：
- 重新排列 Token 字段，按大小排序：`span (u32*2) → kind (u8) → ...`
- 消除 alignment 空隙，减少每个 Token 大小，提高缓存命中率。

---

#### 2. 字符串 interning（字符串驻留）

**问题**：相同标识符（如 `int`, `return`, `i`）在不同地方重复分配，浪费内存，比较慢。

**方案**：
- 启动时预intern 所有关键字。
- lexer 识别标识符后，先查 interning 表，如果已有则复用引用，否则插入。
- 标识符比较变成指针比较，O(1) 常数时间。
- 减少内存占用，加快符号表查找。

**注意**：
- 只 intern 标识符，不 intern 字面量字符串。
- 用 `HashMap<&str, &str>` 存储，arena 分配新字符串。

---

#### 3. 增量位置编码

**问题**：每个 Token 存 (line, column)，占 8 字节，可以压缩。

**方案**：
- 存起始字节偏移 `u32`，长度 `u16`，line 用增量计算需要时算。
- 每个 Token 节省 4-8 字节，缓存命中率更高。

---

### 第六层：算法层面优化

#### 1. 提前剪枝不可达分支

**问题**：当前解析完整个函数体才检查括号匹配，可以提前发现错误退出。

**方案**：
- 跟踪括号/大括号深度，深度为负立即报错，不用继续解析。
- 对于深度嵌套错误，提前退出节省时间。

---

#### 2. 去标签化控制流

**问题**：当前递归下降很多 `loop { match ... }`，用大量 goto/break，可能影响优化。

**方案**：
- 重构为清晰的循环结构，让编译器更好做优化。
- 减少不必要的分支，提高 ICC。

---

## 实施优先级（从高到低，见效从快到慢）

| 优先级 | 优化项 | 预计改动 | 预计收益 | 风险 |
|--------|--------|----------|----------|------|
| 1 | Arena 分配 AST | 中 | ✅️ 大（减少大量分配） | 低（只改分配，逻辑不变） |
| 2 | 查表法字符分类 | 小 | ✅️ 中（词法提速） | 极低 |
| 3 | 字符串 interning | 小 | ✅️ 中（内存少，查找快） | 低 |
| 4 | Pratt 表达式解析 | 大 | ✅️ 中（表达式解析快，减少栈溢出） | 中（表达式逻辑重写，需要回归） |
| 5 | 宏展开缓冲区复用 | 小 | ✅️ 小到中（预处理器提速） | 低 |
| 6 | Token 紧凑打包 | 小 | ✅️ 小（缓存更好） | 极低 |
| 7 | 预读块读取 | 中 | ✅️ 小 | 低 |
| 8 | 标识符指纹快速比较 | 小 | ✅️ 小 | 低 |
| 9 | 惰性 token 生成 | 中 | ✅️ 小（峰值内存低） | 中 |

## 方案修订：实施前置条件与全局约束

原方案中的收益数字属于待验证假设，不能直接作为验收标准。所有优化必须先完成基线测量，并以真实 profile 数据决定优先级。

### 一、建立性能基线

在修改实现前，建立可重复的 benchmark 集合，至少覆盖：

- 小型 C 文件：验证固定开销。
- 大型 C 文件：验证吞吐量和峰值内存。
- 预处理器密集文件：大量 include、宏、条件编译。
- 解析器密集文件：复杂声明、表达式、嵌套类型。
- GNU/C23 扩展密集文件：验证兼容性与诊断开销。

每次 benchmark 至少记录：

- 预处理、词法、语法解析、AST 构建各阶段耗时；
- token 数量、AST 节点数量和 include 文件数量；
- 分配次数、分配总字节数和峰值 RSS；
- 最大递归深度、宏展开次数和缓存命中率；
- 失败诊断数量以及诊断位置处理耗时。

性能目标必须基于基线制定。没有 profile 证据的优化不得承诺固定百分比收益。

建议提供统一命令生成结果，例如：

```text
dcc --profile-parse input.c
```

输出机器可读的 JSON 或稳定的文本格式，供 CI 比较回归。

### 二、预处理器优先优化

对大型工程而言，预处理器可能比语法解析器更早成为瓶颈。因此在 AST 重构前优先分析：

- include 文件缓存和 include guard 检测；
- include 路径搜索与重复 stat/open；
- 宏展开中的 token 复制、字符串拼接和参数替换；
- 条件编译表达式求值；
- 预定义宏查找；
- `#line`、文件名和源位置映射；
- 宏递归检测和展开栈管理。

实现方向：

1. 为规范化后的 include 路径建立内容缓存；
2. 对已确认的 include guard 或 `#pragma once` 快速跳过；
3. 用 token 片段和区间引用减少宏展开复制；
4. 复用宏展开工作缓冲区，但嵌套展开必须使用显式栈帧，不能共享可变缓冲区；
5. 将预处理器输出抽象为可回退的 token stream，保留必要的回溯和诊断位置。

缓存必须明确失效条件：文件内容变化、编译选项变化、预定义宏变化、include 搜索路径变化和语言标准变化。

### 三、字符串驻留改为 SymbolId 设计

`HashMap<&str, &str>` 仍需进行字符串 hash，不能直接等同于指针比较。建议引入统一的 `SymbolTable`：

- lexer 将标识符转换成 `SymbolId`；
- token、AST、符号表和诊断内部统一保存 `SymbolId`；
- 只有需要输出源码或诊断时才通过 `SymbolId` 查询字符串；
- 关键字使用预分配的固定 ID；
- 普通标识符按内容去重，但字符串字面量不默认驻留。

需要保留源文本 slice 或 offset，以支持精确诊断和宏展开，不应让 interning 替代源位置信息。

### 四、Arena 重构改为分阶段节点池

直接把 AST 中的 `Box<T>` 全部改成 `&'ast T` 风险过高，会影响生命周期、可变访问、递归构造、优化 pass 和跨阶段保存。采用以下渐进路线：

1. 先统计 AST 各节点类型的数量和分配热点；
2. 引入只供 parser 使用的 typed node pool 或 index arena；
3. 第一阶段只替换高频、无 `Drop` 的节点；
4. 用稳定的 `NodeId` 或索引引用节点，避免到处传播生命周期参数；
5. 完成 AST、语义分析、IR 和测试迁移后，再评估是否需要彻底移除 `Box`；
6. 对字符串、诊断文本和需要独立生命周期的数据单独管理，不能无条件放入 arena。

节点池必须支持：稳定引用、递归构造、可变访问规则、错误路径释放和 debug 构建下的边界检查。不得为了性能直接引入未经证明安全的 `unsafe`。

### 五、lexer 优化以 profile 为依据

字符分类查表、批量扫描和预读缓冲区只有在 profile 证明边界检查或字符分类占主要耗时时才实施。优先采用安全的 `&[u8]` 批量扫描和标准库 `memchr` 类能力；只有明确证明收益后才考虑 `unsafe`。

优化必须保持：

- EOF 和非 ASCII 字节处理一致；
- 行列号和 byte offset 一致；
- 注释、字符串、字符常量和 digraph/trigraph 行为一致；
- 超长 token 不发生整数溢出。

### 六、表达式 parser 采用 A/B 迁移

Pratt parser 不应直接替换全部递归下降逻辑。实施时：

1. 明确定义 token 到 AST 的运算符优先级、结合性和求值顺序表；
2. 先实现独立 parser，与现有实现并行运行；
3. 对同一输入比较 AST 结构、类型信息和诊断结果；
4. 覆盖 GNU 扩展、逗号表达式、条件表达式、赋值、sizeof、复合字面量和语句表达式；
5. 通过 benchmark 确认收益后，再按表达式类别逐步切换；
6. 保留旧实现作为 debug 或回退路径，完成稳定周期后再删除。

表达式深度问题应优先通过显式操作数栈或受控递归解决，不能只依赖 Pratt parser 宣称解决。

### 七、正确性与兼容性验收

每个优化阶段必须验证：

- 预处理输出与基线一致；
- AST 语义结构与基线一致；
- 生成代码的运行结果与基线一致；
- GCC/C23/GNU 扩展和诊断位置不回退；
- 大文件、深嵌套、超长标识符和错误输入不崩溃；
- 多文件编译、缓存失效和并行编译不会共享错误状态。

仅比较 `-S` 文本不足以验证正确性；机器码相关结论应使用 `objdump -d` 或运行时测试确认。

### 八、修订后的实施顺序

| 阶段 | 内容 | 前置条件 |
|------|------|----------|
| 0 | benchmark、profile、分配和内存基线 | 必须先完成 |
| 1 | include 缓存、guard 快速路径、宏展开复用 | 基线确认预处理器为热点 |
| 2 | token 紧凑化、SymbolId、token buffer 复用 | 保持诊断 offset 不变 |
| 3 | lexer 查表和批量扫描 | profile 确认 lexer 为热点 |
| 4 | typed node pool，逐步替换高频 AST 分配 | 完成 AST 分配统计 |
| 5 | Pratt parser A/B 迁移 | 完成语义等价测试 |
| 6 | 惰性 token stream | 明确回退、宏栈和 include 生命周期 |
| 7 | 全量 arena 或更激进重构 | 只有前阶段收益明确时实施 |

每个阶段应独立提交、独立 benchmark 和独立回归。若收益低于维护成本，应停止该阶段，而不是为了完成路线图强行重构。
